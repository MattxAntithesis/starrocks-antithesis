# What StarRocks' own bug history says to test

A workload finds bugs where it looks. This is a pass over StarRocks' merged
`[BugFix]` pull requests, to aim the next version of `loads/` at the places the
project actually breaks, rather than at guarantees chosen in the abstract.

## Method

Ten GitHub searches over `repo:StarRocks/starrocks is:pr is:merged [BugFix] in:title`,
each narrowed by one term (`primary key`, `transaction`, `publish`, `stream load`,
`compaction`, `tablet`, `replica`, `partial update`, `data loss`, `insert`), 100 PRs
each, newest first. That is **833 unique PRs, 338 distinct fixes** once each fix is
grouped with its backports.

Each search reports far more matches than 100 (`tablet` alone matches 865), so this is
a recent-weighted sample, not the whole history. It is enough to rank themes; it is not
a census.

**Backports rank severity.** `AGENTS.md` says bug-fix PRs set version checkboxes that
drive auto-backporting, so a fix carried into release branches is one that reached
users. Grouping each fix with its backports gives a severity signal for free.

The first two are the same shape: **a load or a transaction running concurrently with a
schema change**. That is precisely what the current workload never does.

## What `loads/` covers, and what it misses

Covered today: INSERT, DELETE, Stream Load (FE and BE), SQL transactions over two
tables, the Stream Load transaction interface including PREPARED transactions left to
commit later, label reuse under retry, and reads checked against a model, all under
kills, partitions, clogs, pauses and clock skew.

Missing, in the order the history ranks it:

1. **Partial column updates.** 31 fixes, 28 backported, and the cluster of
   most-backported fixes above is dominated by them — including one named for
   *share nothing*, the mode under test. The workload sends none. Needs
   `partial_update`, `partial_update_mode=column`, `merge_condition` (conditional
   update) and an `AUTO_INCREMENT` column, which three separate fixes interact with.
2. **Schema change concurrent with loads and PREPARED transactions.** Two distinct
   data-loss fixes (`#82114`, `#34928`). The workload already produces PREPARED
   transactions, so adding `ALTER TABLE` while they are open reaches the second one's
   shape directly. Compaction and `ALTER TABLE OPTIMIZE` were out of the agreed scope;
   the history argues for putting them back in.
3. **Non-integer column types.** Every column in `kv`, `ev` and `ev2` is `INT` or
   `BIGINT`. *Return CHAR unpadded from a primary-key point lookup* is a correctness
   bug the current schema cannot express. `CHAR`, `VARCHAR`, `DATE` and `DECIMAL`
   columns cost nothing to add.
4. **Replica repair as a checked outcome.** 42 fixes around clone, decommission and
   repair. The workload creates the conditions (BE kills, `some tablets are unhealthy`
   passes) but only ever checks data, never that repair converges.
5. **Shared-data (lake) mode.** Several recent primary-key fixes are lake-only. The
   deployment under test is shared-nothing, so that half of the product is untested
   here. This is a deployment change (object storage), not a driver change.

## Suggested order

1. Partial column updates with conditional updates and auto-increment.
2. `ALTER TABLE` (including `OPTIMIZE`) concurrent with loads and open PREPARED
   transactions, plus compaction pressure.
3. Wider column types.
4. Instrument the BE (see FINDINGS.md): thread pausing currently covers only the FE's
   JVM, and every theme above lives in `starrocks_be`.

## Steering, instead of shooting in the dark

Antithesis explores preferentially from moments that reach a `Sometimes` assertion, and
a *rich* one (`assert_sometimes_greater_than!`, `assert_sometimes_all!`) also tells it
how close a moment came, so it climbs toward the state instead of waiting to stumble
into it. Exploration assertions are therefore the steering wheel, and the themes above
are the destinations.

The obstacle was that the dangerous states live inside the BE, which is an official
image we cannot add assertions to. But StarRocks exposes BE internals over plain SQL,
so the driver can read them and steer on them with no instrumented build:

| Bug theme | Observable (via `information_schema`) | Assertion that steers toward it |
| --- | --- | --- |
| compaction (50 fixes) | `be_tablets.NUM_ROWSET`, `be_compactions.LATEST_COMPACTION_SCORE`, `CANDIDATE_MAX_SCORE` | `assert_sometimes_greater_than!(max_rowsets, 20, ...)` — climbs toward version pile-up, which is what triggers compaction |
| publish version (51) | `be_txns.COMMIT_TIME` set with `PUBLISH_TIME` unset | `assert_sometimes_greater_than!(committed_unpublished, 0, ...)` — climbs toward the publish window where these bugs live |
| schema change vs PREPARED txn (#34381, data loss) | open PREPARED label + a running `ALTER` on the same table | `assert_sometimes_all!({prepared_txn_open, alter_running, same_table}, ...)` — works toward all three true at once |
| partial update / column mode (31) | the driver's own request shape | `assert_sometimes_all!({partial_update, merge_condition, auto_increment}, ...)` |
| replica / clone / repair (42) | `fe_tablet_schedules.STATE`, `SCHEDULE_REASON` | steer toward a repair in flight, then assert it converges once faults stop |
| primary key index / rowset (46) | `be_tablets` per replica | see the divergence oracle below |

### A replica-divergence oracle, available today

`be_tablets` reports `NUM_ROW`, `NUM_ROWSET`, `MAX_VERSION` and `DATA_SIZE` **per BE per
tablet**. Two replicas of one tablet at the same `MAX_VERSION` must hold the same
`NUM_ROW`. The workload's current checks all read through the FE, which serves one
replica, so a diverged replica is invisible to them; this compares the replicas
directly. It is the cheapest new oracle available and it points straight at the
largest backported cluster (primary key index / rowset / delvec consistency), without
needing an instrumented BE.

Caveat: these tables query the BEs live, so they fail or time out under faults. Treat a
failed read as no information, never as a violation.
